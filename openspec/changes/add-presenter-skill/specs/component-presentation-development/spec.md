# Spec Delta

## Purpose

Вынести логику подготовки данных для отображения в чистые функции, которые легко покрыть unit-тестами. Компонент использует результаты этих функций для отображения.

## ADDED Requirements

### Requirement: Presentation workflow
Skill `gost-view-presenter` SHALL на английском описывать выделение и изменение чистых функций подготовки представления с явными входными данными и контекстом. Он MUST работать с обычными props и данными, сохраняя существующие источники данных, зависимости и обработку событий проекта. Skill MUST NOT добавлять инфраструктуру состояния ради presenter.

#### Scenario: Extract component calculations
- **WHEN** компонент с обычными props содержит вычисления представления
- **THEN** skill выносит их в чистые функции, компонент получает готовые результаты
- **AND** зависимости и организация состояния проекта сохраняются

#### Scenario: Preserve an existing application
- **WHEN** компонент уже получает данные и callbacks через существующие привязки
- **THEN** привязки, callbacks и поведение событий сохраняются
- **AND** presenter работает только с переданными данными

### Requirement: Pure composable functions
Presenters MUST детерминированно вычислять результат из явных входов, сохраняя их неизменность. Побочные эффекты и скрытые чтения состояния исключены. Связанные вычисления SHALL группироваться при общей работе; независимые функции могут использоваться отдельно и в композиции.

#### Scenario: Test independent and combined calculations
- **WHEN** нужны связанные признаки состояния и независимое форматирование списка
- **THEN** функции можно вызвать отдельно или собрать их результаты в общей функции
- **AND** тесты проверяют результаты, неизменность входов и явность зависимостей

#### Scenario: Hidden dependency is found
- **WHEN** вычисление неявно читает состояние, время или locale либо вызывает побочный эффект
- **THEN** необходимые данные передаются явно, а побочный эффект остаётся снаружи
- **AND** недостающий обязательный контекст указывается как проблема

### Requirement: Ready view data and reactive integration
Skill SHALL переносить условия отображения, форматирование и преобразования коллекций в presenter; компонент использует готовые поля, boolean-признаки и списки. Реактивная привязка MUST обновлять результат при изменении входов. Для компонента с готовыми данными дополнительный presenter не требуется.

#### Scenario: Move inline presentation logic
- **WHEN** компонент вычисляет условия, форматирует данные или применяет filter/map/sort, в том числе внутри derived/helper
- **THEN** вычисления переносятся в presenter, разметка использует готовые значения
- **AND** if/else-if читает готовый boolean, обычный else и чтение полей строк списка допустимы

#### Scenario: Keep simple components simple
- **WHEN** компонент получает готовые props и не выполняет вычислений
- **THEN** skill сохраняет существующую структуру компонента
- **AND** события и работа с браузерными API сохраняются

#### Scenario: Change reactive inputs
- **WHEN** входы presenter меняются в Svelte 5 компоненте
- **THEN** текст, условные ветки и строки списка обновляются через существующую привязку
- **AND** результат остаётся вычисляемым значением с одним источником данных

### Requirement: Explicit input contracts and source boundaries
Skill MUST проверить типы и варианты входных данных, соглашения проекта и доступность источников рекомендаций. Он SHALL учитывать документированные nullable/loading/empty/error состояния. Проверка внешних данных остаётся на границе приложения; отсутствие обязательного входа указывается явно.

#### Scenario: Use documented variants
- **WHEN** входной контракт предусматривает loading, empty, error, success или nullable-поля
- **THEN** тесты проверяют соответствующие результаты и условия отображения
- **AND** данные поступают согласно проверенному контракту приложения

#### Scenario: Required information is missing
- **WHEN** контракт, контекст или источник рекомендаций не позволяют определить нужное поведение
- **THEN** агент указывает недостающий вход и незавершённую часть работы
- **AND** сохраняет существующие границы проверки данных и работы с состоянием

### Requirement: Observable skill evaluation
Готовность skill MUST подтверждаться полученным кодом и его поведением. Unit-тесты SHALL вызывать presenter как обычную функцию; привязка к компоненту проверяется отдельно. Ошибочные примеры MUST разбираться вручную с объяснением; успешная компиляция подтверждает только синтаксис и типы. Skill MUST NOT создавать новые lint-правила и configs.

#### Scenario: Evaluate creation change and repeat
- **WHEN** независимый агент применяет установленный skill к созданию, изменению и повторной задаче в тестовом проекте
- **THEN** функции, тесты и компоненты проверяются по результатам и обновлению отображения
- **AND** соседние файлы, привязки и callbacks сохранены, повтор использует существующие функции

#### Scenario: Distinguish verification layers
- **WHEN** проверки типов или unit-тесты проходят
- **THEN** отчёт отдельно содержит результаты проверки компонента и ручной оценки примеров
- **AND** недостающие браузерные проверки или проверка харнеса отмечены как ограничение готовности

### Requirement: Separate native plugin delivery
Plugin `gost-view-presenter` SHALL иметь собственные SemVer/changelog и единое дерево skill/reference для Codex и Claude. Оба каталога MUST выбирать его local source в одном snapshot маркетплейса. Содержимое и версии прежних плагинов MUST сохраняться; применение skill к приложению выполняется отдельным действием.

#### Scenario: Install independently and alongside existing plugins
- **WHEN** plugin устанавливается в изолированных профилях обоих харнесов отдельно и рядом с прежними плагинами
- **THEN** новая сессия обнаруживает отдельный skill с читаемым reference и совпадающими файлами
- **AND** повтор сохраняет одну установку, приложение и личные настройки

#### Scenario: Reject invalid delivery
- **WHEN** отсутствует skill/reference, расходятся identity/version или путь выходит за границу plugin root
- **THEN** проверка сообщает конкретный файл и причину отказа
- **AND** готовность установки подтверждается отдельной нативной проверкой

### Requirement: Authoritative rules and separate approval
Skill SHALL ссылаться на существующие источники рекомендаций по чистым функциям и отображению с указанием revision/status. Он MUST сохранять применимость выбранных проектом правил. Reference MUST NOT дублировать нормативные правила или расширять применимость источника. Принятие нормативного содержания, миграции приложений и выпуск требуют отдельных решений.

#### Scenario: Read rules without the author checkout
- **WHEN** установленный skill читает reference и источники рекомендаций
- **THEN** внутренние ссылки работают в plugin, внешние ведут на зафиксированные ревизии либо используются проверенные копии
- **AND** недоступный обязательный источник отмечается как незавершённая проверка

#### Scenario: Prepare an unreleased plugin
- **WHEN** metadata, проверки и review готовы
- **THEN** версия 0.1.0 остаётся unreleased, пять npm-пакетов и proposed/Pending сохраняются
- **AND** merge, выпуск, тег и применение в asc-admin выполняются по отдельным указаниям
