# state-foundation-plugin-distribution Specification

## Purpose

Обеспечить установку общего версионируемого плагина с skill подключения fc/shell через собственные Git-маркетплейсы Codex и Claude Code, сохраняя воспроизводимость поставки и границы подключения приложения.

## Requirements

### Requirement: Native marketplace installation in both harnesses
Плагин SHALL устанавливаться через штатный Git-маркетплейс каждого из Codex и Claude Code. Оба каталога MUST поставлять одну идентичность плагина и один общий skill, без собственного installer и ручного копирования skill пользователем.

#### Scenario: Install into Codex
- **WHEN** пользователь добавляет каталог поддерживаемой ревизии репозитория и устанавливает плагин штатными средствами Codex
- **THEN** в новой сессии Codex обнаруживается skill `gost-svelte-spa-state` установленного плагина
- **AND** для установки не требуется приложение-потребитель

#### Scenario: Install into Claude Code
- **WHEN** пользователь добавляет каталог выбранной поставки с закреплённым commit плагина и устанавливает его штатными средствами Claude Code
- **THEN** в новой сессии Claude Code обнаруживается тот же skill с нативным пространством имён плагина
- **AND** состав skill совпадает с поставкой для Codex

### Requirement: Self-contained common content
Плагин MUST содержать единственное сопровождаемое дерево исходников skill и все его references. Установленный skill SHALL читаться без workspace links, абсолютных путей автора или доступа к исходному checkout. Поставка MUST исключать локальные настройки агентов, review-материалы, consumer source и тестовые fixtures.

#### Scenario: Read the installed recipe
- **WHEN** каждый харнес загружает плагин из отдельной копии репозитория без доступа к исходному checkout
- **THEN** skill и Public API recipe читаются внутри поставки
- **AND** hashes содержимого skill и references совпадают между харнесами

### Requirement: Independent plugin version
Плагин MUST иметь собственную SemVer-версию и changelog. Идентичность и версия в метаданных обоих харнесов MUST совпадать. Изменение версии плагина MUST NOT менять версии пяти пакетов стандартов или объявлять обновлёнными runtime-зависимости и приложения.

#### Scenario: Prepare a plugin-only update
- **WHEN** в disposable копии подготавливается следующая версия плагина
- **THEN** оба харнеса видят одинаковые identity/version и соответствующий changelog
- **AND** версии и содержимое пяти npm-пакетов, а также код приложения-потребителя не меняются

### Requirement: Repeatable selection and explicit updates
Инструкция SHALL описывать выбор точной поставки и определение установленной версии: для Claude commit выбирает сопровождающий через каталог, для Codex фиксируется Git-ревизия каталога. Повторная установка MUST NOT дублировать skill. Штатное обновление SHALL доставлять выбранную новую поставку с описанными ограничениями каждого харнеса; произвольный пользовательский SHA-selector в Claude не обещается.

#### Scenario: Repeat an installation
- **WHEN** плагин той же ревизии повторно подключается в том же изолированном профиле
- **THEN** доступен один логический skill плагина и прежнее содержимое references

#### Scenario: Update a selected distribution
- **WHEN** профиль обновляется с одной проверенной ревизии на другую штатным поддерживаемым способом
- **THEN** после требуемого перезапуска обнаруживаются новая версия и новое содержимое
- **AND** результат подтверждается установленными файлами, а не только version string каталога

### Requirement: Claude catalog pins the plugin source
Каталог Claude MUST закреплять полный commit SHA источника плагина и путь к его общему дереву в том же репозитории. Закреплённая поставка MUST совпадать по identity/version и содержимому с соответствующей поставкой Codex. Невалидный или недоступный pin, неправильный путь и расхождение содержимого MUST NOT приводить к подстановке другой ревизии или успешному отчёту.

#### Scenario: Maintainer prepares a pinned catalog
- **WHEN** сопровождающий добавляет в каталог полный commit SHA уже подготовленного плагина
- **THEN** Claude получает именно этот plugin tree, а hashes соответствующей поставки Codex совпадают
- **AND** Git-ревизия каталога и Git-ревизия содержимого могут различаться и записываются отдельно

#### Scenario: Invalid or unavailable source pin
- **WHEN** pin отсутствует, не является полным SHA, недоступен либо указывает на другое содержимое или путь
- **THEN** проверка сообщает конкретное расхождение и результат остаётся incomplete
- **AND** плавающая ветка и локальное рабочее дерево не используются как замена

### Requirement: Invalid distribution is not reported as complete
Проверка поставки MUST отклонять несовпадающие identity/version, невалидные метаданные, отсутствующие skill/reference и файловые ссылки за пределы plugin root. Внешние HTTP(S) URI документации MUST NOT считаться локальными файлами или нарушением containment. Недоступный источник, неподдерживаемый харнес или отсутствие evidence нативной установки SHALL означать incomplete.

#### Scenario: Broken plugin content
- **WHEN** disposable поставка содержит несовпадающую версию, отсутствующий reference или файловый путь за пределы плагина
- **THEN** проверка сообщает конкретное расхождение и не подтверждает готовность поставки

#### Scenario: External documentation URI
- **WHEN** корректный skill содержит внешнюю HTTPS-ссылку на документацию gost-kit и локальный reference внутри plugin root
- **THEN** внешняя ссылка не проверяется как локальный файл и не вызывает containment-отказ
- **AND** локальный reference по-прежнему проверяется на существование и containment

#### Scenario: File URI outside plugin root
- **WHEN** ссылка с URI-схемой `file:` указывает за пределы plugin root
- **THEN** проверка отклоняет её как файловую ссылку за пределы поставки
- **AND** наличие URI-схемы не позволяет обойти файловый containment

#### Scenario: One harness cannot be verified
- **WHEN** отсутствует поддерживаемый харнес или его штатная установка недоступна
- **THEN** результат явно указывает непроверенный харнес и причину
- **AND** успешная установка во втором харнесе не засчитывается за оба

### Requirement: Installation preserves application boundaries
Установка и обновление плагина MUST NOT изменять приложение или автоматически запускать skill подключения fc/shell. При явном применении skill SHALL сохранять требования `svelte-spa-state-foundation`, включая проверку реальных зависимостей, отдельность миграции фич и явное сообщение о недоступных артефактах.

#### Scenario: Install without applying the skill
- **WHEN** пользователь устанавливает либо обновляет плагин рядом с synthetic SPA
- **THEN** hashes файлов приложения сохраняются
- **AND** подключение fc/shell требует отдельного явного вызова skill

### Requirement: Isolated evidence and separate release approval
Проверка готовности SHALL включать установку, обнаружение и чтение references в изолированных профилях обоих харнесов с зафиксированными версиями и ревизиями. Она MUST NOT менять личные настройки пользователя. Проверки, согласование плана и реализация MUST NOT означать разрешение merge, публикации, release tags или принятие нормативных стандартов.

#### Scenario: Verify before release
- **WHEN** проверки завершены для обоих харнесов
- **THEN** отчёт содержит команды, версии, ревизии, hashes поставки, результаты и ограничения
- **AND** личные профили сохранены, а выпуск остаётся отдельным действием по явному разрешению
