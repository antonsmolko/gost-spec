# state-foundation-plugin-distribution Specification

## Purpose

Обеспечить установку общего версионируемого плагина с skill подключения fc/shell через собственные Git-маркетплейсы Codex и Claude Code, сохраняя воспроизводимость поставки и границы подключения приложения.

## Requirements

### Requirement: Native marketplace installation in both harnesses
Плагин SHALL устанавливаться штатными Git-маркетплейсами Codex и Claude Code как `gost-svelte-shell` с единственным skill того же имени. Оба каталога MUST выбирать одно общее дерево shell-плагина из выбранного snapshot без собственного installer и ручного копирования. Каталоги SHALL допускать отдельные независимо версионируемые плагины; их установка MUST NOT менять идентичность, содержимое или версию shell-плагина.

#### Scenario: Install into Codex
- **WHEN** пользователь добавляет каталог существующего release tag репозитория и устанавливает плагин штатными средствами Codex
- **THEN** в новой сессии Codex обнаруживается skill `gost-svelte-shell` установленного плагина с нативным пространством имён
- **AND** для установки не требуется приложение-потребитель

#### Scenario: Install into Claude Code
- **WHEN** пользователь добавляет каталог того же release tag и устанавливает плагин штатными средствами Claude Code
- **THEN** в новой сессии Claude Code обнаруживается тот же skill с нативным пространством имён плагина
- **AND** версия и полное дерево плагина совпадают с поставкой для Codex

#### Scenario: Another plugin shares the marketplace
- **WHEN** пользователь отдельно устанавливает `gost-functional-core` из того же marketplace snapshot
- **THEN** `gost-svelte-shell` остаётся отдельной доступной для установки entry со своей identity/version и одним skill
- **AND** при установке обоих плагинов их skills различаются по native namespace; второй не подменяет первый и не запускает подключение основы

### Requirement: Self-contained common content
Плагин MUST содержать единственное сопровождаемое дерево исходников skill и все его references. Установленный skill SHALL читаться без workspace links, абсолютных путей автора или доступа к исходному checkout. Поставка MUST исключать локальные настройки агентов, review-материалы, consumer source и тестовые fixtures.

#### Scenario: Read the installed recipe
- **WHEN** каждый харнес загружает плагин из отдельной копии репозитория без доступа к исходному checkout
- **THEN** skill и Public API recipe читаются внутри поставки
- **AND** hashes содержимого skill и references совпадают между харнесами

### Requirement: Independent plugin version
Плагин MUST иметь собственную SemVer-версию и changelog. Идентичность и версия в метаданных обоих харнесов MUST совпадать. Изменение версии плагина MUST NOT менять версии пакетов стандартов или объявлять обновлёнными runtime-зависимости и приложения.

#### Scenario: Prepare a plugin-only update
- **WHEN** в disposable копии подготавливается следующая версия плагина
- **THEN** оба харнеса видят одинаковые identity/version и соответствующий changelog
- **AND** версии и содержимое npm-пакетов стандартов, а также код приложения-потребителя не меняются

### Requirement: Repeatable selection and explicit updates
Инструкция SHALL описывать выбор существующего release tag обоими харнесами и определение установленной версии и содержимого. Повторная установка MUST NOT дублировать skill. Переход на другой тег и возврат SHALL выполняться явно штатными средствами с описанием последствий перерегистрации каталога. Обновление выбранного тега MUST NOT означать переход на main или на другой выпуск.

#### Scenario: Repeat an installation
- **WHEN** плагин того же release tag повторно подключается в том же изолированном профиле
- **THEN** доступен один логический skill плагина и прежнее содержимое references

#### Scenario: Update a selected distribution
- **WHEN** профиль явно переводится с одного проверенного release tag на другой штатным поддерживаемым способом
- **THEN** после требуемого перезапуска обнаруживаются новая версия и новое содержимое
- **AND** результат подтверждается установленными файлами, а не только version string каталога

#### Scenario: Return to an earlier released version
- **WHEN** пользователь явно выбирает прежний доступный release tag, заново устанавливает плагин при необходимости и перезапускает сессию
- **THEN** активен один skill с версией и полным содержимым прежнего выпуска
- **AND** приложение сохраняется; последствия удаления каталога для других плагинов описаны до команды удаления

#### Scenario: Selected release cannot be installed
- **WHEN** выбранный тег или его содержимое недоступны либо фактически установленные файлы не соответствуют выбранному выпуску
- **THEN** результат сообщает incomplete, причину и фактическое состояние установки
- **AND** main, другой тег или ранее закешированная версия не выдаются за выбранную поставку

### Requirement: Invalid distribution is not reported as complete
Проверка поставки MUST отклонять несовпадающие identity/version, невалидные метаданные, отсутствующие skill/reference и файловые ссылки за пределы plugin root. Внешние HTTP(S) URI документации MUST NOT считаться локальными файлами или нарушением containment. Недоступный источник, неподдерживаемый харнес или отсутствие evidence нативной установки SHALL означать incomplete.

#### Scenario: Broken plugin content
- **WHEN** disposable поставка содержит несовпадающую версию, отсутствующий reference или файловый путь за пределы плагина
- **THEN** проверка сообщает конкретное расхождение и не подтверждает готовность поставки

#### Scenario: External documentation URI
- **WHEN** корректный skill содержит внешнюю HTTPS-ссылку на документацию gost-kit и локальный reference внутри plugin root
- **THEN** внешняя ссылка не проверяется как локальный файл и не вызывает containment-отказ
- **AND** локальный reference по-прежнему проверяется на существование и containment

#### Scenario: File URI outside plugin root
- **WHEN** ссылка с URI-схемой `file:` указывает за пределы plugin root
- **THEN** проверка отклоняет её как файловую ссылку за пределы поставки
- **AND** наличие URI-схемы не позволяет обойти файловый containment

#### Scenario: One harness cannot be verified
- **WHEN** отсутствует поддерживаемый харнес или его штатная установка недоступна
- **THEN** результат явно указывает непроверенный харнес и причину
- **AND** успешная установка во втором харнесе не засчитывается за оба

### Requirement: Installation preserves application boundaries
Установка и обновление плагина MUST NOT изменять приложение или автоматически запускать skill подключения fc/shell. При явном применении skill SHALL сохранять требования `svelte-spa-state-foundation`, включая проверку реальных зависимостей, отдельность миграции фич и явное сообщение о недоступных артефактах.

#### Scenario: Install without applying the skill
- **WHEN** пользователь устанавливает либо обновляет плагин рядом с synthetic SPA
- **THEN** hashes файлов приложения сохраняются
- **AND** подключение fc/shell требует отдельного явного вызова skill

### Requirement: Isolated evidence and separate release approval
Проверка готовности SHALL включать установку, обнаружение и чтение references в изолированных профилях обоих харнесов с зафиксированными версиями и ревизиями. Она MUST NOT менять личные настройки пользователя. Проверки, согласование плана и реализация MUST NOT означать разрешение merge, публикации, release tags или принятие нормативных стандартов.

#### Scenario: Verify before release
- **WHEN** проверки завершены для обоих харнесов
- **THEN** отчёт содержит команды, версии, ревизии, hashes поставки, результаты и ограничения
- **AND** личные профили сохранены, а выпуск остаётся отдельным действием по явному разрешению

### Requirement: Explicit migration between plugin identities
Переход с `gost-svelte-spa-state` на `gost-svelte-shell` SHALL описываться как смена идентичности с явным удалением прежней установки и установкой новой. Документация MUST различать возврат к существующему релизному тегу и восстановление прежней поставки без тега. Автоматическое переименование штатным update MUST NOT обещаться. Миграция поставки MUST NOT изменять приложение или расширять совместимость skill.

#### Scenario: Replace an existing installation
- **WHEN** пользователь выполняет документированный переход со старого plugin ID на новый штатными средствами поддерживаемого харнеса
- **THEN** после нужного перезапуска обнаруживается один новый skill с доступным recipe, а старый plugin skill больше не активен
- **AND** код приложения сохраняется

#### Scenario: New installation uses the shorter name
- **WHEN** пользователь впервые устанавливает новую поставку
- **THEN** документация, каталог, metadata и native discovery согласованы с `gost-svelte-shell`
- **AND** поддержка существующего Svelte 5 SPA и обязательная основа fc/shell сохраняются

#### Scenario: A migration cannot finish
- **WHEN** установка новой поставки после удаления старой не завершается
- **THEN** результат явно сообщает incomplete и фактически активную идентичность
- **AND** прежний plugin ID не выдаётся за успешную установку нового

#### Scenario: Explicit return to the previous delivery
- **WHEN** пользователь явно возвращается к прежней доступной поставке с old ID
- **AND** для legacy-поставки без release tag используется документированный прежний catalog/content workflow: Codex выбирает прежний catalog commit, а для Claude мейнтейнер восстанавливает old entry, ID, source.sha и совпадающую поставку Codex
- **THEN** после удаления новой идентичности, явной установки прежней и нужного перезапуска активен один прежний skill с доступным recipe и проверенным прежним содержимым
- **AND** код приложения сохраняется; возврат не выдаётся за успешную миграцию на новый ID и не выполняется как скрытый fallback
- **AND** legacy-поставка восстанавливается в отдельном историческом snapshot и проверяется процессом соответствующей ревизии; результат подтверждает восстановление прежнего содержимого, а не готовность новой релизной поставки
- **AND** текущая проверка новой релизной поставки SHALL по-прежнему отклонять legacy `git-subdir` source; её успешное прохождение не требуется для этого исторического возврата, и legacy-каталог не подставляется в текущий релизный snapshot

#### Scenario: Claude rollback is not available yet
- **WHEN** у прежней legacy-поставки нет доступного release tag и её catalog entry и content pin ещё не восстановлены мейнтейнером
- **THEN** документация сообщает, что legacy-возврат Claude недоступен до восстановления каталога, без обещания несуществующего тега или произвольного SHA-selector
- **AND** фактически активная идентичность сообщается явно; успешный rollback не заявляется

### Requirement: Catalog sources stay within the selected snapshot
Оба каталога MUST выбирать общее дерево плагина локальным относительным источником внутри выбранного snapshot маркетплейса. Отдельный same-repository content SHA MUST NOT требоваться. Перенаправление источника вне этого дерева MUST отклоняться проверкой поставки; существующие проверки содержимого, ссылок, метаданных и приватности сохраняются.

#### Scenario: Both catalogs select the same tree
- **WHEN** оба харнеса устанавливают плагин из одного проверенного snapshot маркетплейса
- **THEN** оба получают полное общее дерево, включая manifests, skill, recipe, icon, license, README и changelog
- **AND** поставка не зависит от доступности прежнего отдельного content commit

#### Scenario: Catalog points elsewhere
- **WHEN** источник каталога выбирает другой каталог, внешний Git-источник, абсолютный путь или выход за пределы общего plugin directory
- **THEN** проверка отклоняет поставку с указанием файла каталога и причины

### Requirement: Releases use immutable versioned marketplace tags
Релиз плагина SHALL обозначаться тегом `gost-svelte-shell-v<SemVer>` на фактическом main commit после merge проверенного PR и отдельного release approval. Версия тега MUST совпадать с manifests и changelog. Опубликованный тег MUST NOT перемещаться, заменяться или переиспользоваться. Тег выбирает snapshot всего маркетплейса, а не независимые версии его отдельных записей.

#### Scenario: Release after an ordinary merge
- **WHEN** PR вмержен обычным merge, squash или rebase и владелец отдельно разрешил конкретный выпуск
- **THEN** тег создаётся на итоговой проверенной ревизии main, содержащей выпускаемый плагин и оба каталога
- **AND** отдельный content commit в истории main и тег для каждого рабочего commit не требуются

#### Scenario: Record an identifiable release
- **WHEN** готовится выпуск
- **THEN** evidence связывает имя тега, его resolved commit, версию manifests, changelog и hashes поставки
- **AND** версии остальных пакетов не выводятся из имени этого тега

#### Scenario: Reject a mismatched or reused release
- **WHEN** тег отсутствует при проверке существующего выпуска, указывает на неподходящую ревизию или содержит другую версию, либо подготовка требует изменить уже опубликованный тег
- **THEN** release verification сообщает конкретную причину и не подтверждает выпуск
- **AND** обычная успешная native-установка сама по себе не заменяет проверку тега и версии

### Requirement: Draft validation is independent of release availability
Проверка корректного рабочего дерева SHALL работать без `.git`, сети и существования будущего release tag. Проверка конкретного выпуска SHALL отдельно проверять его тег, ревизию и установленное содержимое. Отсутствие native evidence или недоступность харнеса MUST оставлять готовность поставки incomplete, даже если проверка файлов проходит.

#### Scenario: Validate before creating a tag
- **WHEN** корректная ещё не выпущенная поставка проверяется в копии файлов без `.git` и без опубликованного тега
- **THEN** проверка файлов проходит без создания тега и поиска исторических Git-объектов
- **AND** это не объявляется публикацией или доказательством нативной установки

#### Scenario: Verify an integrated main checkout
- **WHEN** после обычной интеграции PR проверяется checkout, полученный только из main
- **THEN** валидная поставка проходит без объектов боковой ветки или вспомогательных content commits

#### Scenario: Native evidence is missing
- **WHEN** проверка файлов проходит, но выбранный выпуск не проверен установкой и discovery в одном из харнесов
- **THEN** отчёт отдельно указывает успешную проверку файлов и incomplete native readiness с причиной
