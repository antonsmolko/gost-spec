# svelte-spa-state-foundation Specification

## Purpose

Обеспечить воспроизводимое подключение основы fc/shell к существующему Svelte 5 SPA с помощью переиспользуемого skill, сохраняя миграцию бизнес-фич отдельной работой.

## Requirements

### Requirement: Existing application integration
Skill SHALL подключать основу fc/shell к существующему Svelte 5 SPA: зависимости, корневую композицию состояния и reducers, effector и доступ к реактивному store. Skill MUST учитывать структуру и инструкции проекта потребителя.

#### Scenario: Connect a supported SPA
- **WHEN** skill применяется к поддерживаемому SPA без fc/shell
- **THEN** приложение получает работающую основу управления состоянием и проходит свои применимые проверки
- **AND** создание нового проекта не требуется

### Requirement: Business migration remains separate
Skill MUST NOT переносить существующие бизнес-состояния, авторизацию или фичи на fc/shell и MUST NOT составлять план их переписывания как часть подключения.

#### Scenario: Existing authentication and unfinished feature
- **WHEN** в приложении уже есть авторизация и начата другая фича
- **THEN** подключение основы не переписывает их бизнес-логику
- **AND** дальнейшая миграция требует отдельной задачи

### Requirement: Composable application foundation
Подключение SHALL предоставлять общую точку композиции состояния, reducers и обработчиков effects. Оно MUST позволять добавлять общеприкладные модули и фичи без создания отдельного shell для каждой фичи. Базовое подключение MUST NOT генерировать модалки, алерты или иные бизнес-возможности без текущего требования.

#### Scenario: Foundation without shared business modules
- **WHEN** приложение пока не требует общеприкладных модулей
- **THEN** основа работоспособна без придуманных бизнес-состояний и демонстрирует возможность дальнейшей композиции

### Requirement: Reuse an existing connection
Skill MUST сначала проверять наличие fc/shell. При совместимом существующем подключении он SHALL переиспользовать его; при несовместимом или неоднозначном подключении SHALL описать расхождение до изменения затронутой конфигурации.

#### Scenario: Repeated invocation
- **WHEN** skill повторно запускается на уже подготовленном приложении
- **THEN** не создаются дублирующие store, shell или корневые обработчики

### Requirement: Explicit dependency compatibility
Skill SHALL проверять фактические версии, публичные API, engines и peer dependencies выбранных артефактов и документировать проверенную опубликованную связку. При недоступных артефактах или неподтверждённой совместимости он MUST сообщать ограничение и MUST NOT заявлять успешное подключение либо заменять библиотеку собственной реализацией.

#### Scenario: Unavailable package
- **WHEN** требуемый пакет отсутствует в доступном источнике установки
- **THEN** агент сообщает, какой артефакт необходим, и не использует неподтверждённую команду установки как доказательство успеха

#### Scenario: Verify a published pair
- **WHEN** рецепт обозначает опубликованную связку как проверенную
- **THEN** evidence содержит версии, источник и идентичность реально установленных пакетов, среду и результаты проверок
- **AND** одних registry metadata или локального workspace недостаточно

#### Scenario: Incompatible consumer environment
- **WHEN** среда потребителя не удовлетворяет engines либо peer range выбранной связки
- **THEN** skill сообщает конкретную несовместимость и оставляет зависимое подключение incomplete
- **AND** не обновляет среду потребителя молча

### Requirement: Observable verification
Результат подключения SHALL проверяться на независимом существующем SPA через цепочку UI → action → reducer → реактивное обновление UI и применимые проверки потребителя. Проверки MUST подтверждать сохранение существующего поведения и границу отсутствия миграции.

#### Scenario: Verify the connection
- **WHEN** агент завершает подключение в тестовом SPA
- **THEN** он предъявляет результаты проверки цепочки и существующего поведения, а не только наличие файлов или успешную проверку формата skill

### Requirement: Versioned evolution is explicit
Skill SHALL документировать поддерживаемые версии основы и обязательный состав подключения. Будущие общие фичи gost-kit MUST становиться обязательными только после отдельного изменения требований и совместимости. Обновление skill MUST NOT считаться обновлением ранее подготовленного приложения.

#### Scenario: Shared functionality becomes mandatory later
- **WHEN** новая версия skill вводит согласованный обязательный модуль gost-kit
- **THEN** первое подключение использует состав этой версии
- **AND** для ранее подключённых приложений отдельно описываются необходимые изменения и ограничения обновления

### Requirement: Portable skill content
Skill SHALL использовать открытый формат Agent Skills и публичные API gost-kit. Он MUST NOT требовать конкретного AI-продукта или включать приватные исходники, конфигурацию и бизнес-материалы приложения потребителя.

#### Scenario: Use outside the original application
- **WHEN** skill применяется к другому поддерживаемому SPA
- **THEN** инструкции работают без доступа к исходникам asc-admin и без абсолютных путей машины автора

### Requirement: Typed application store context
Для согласованной модульной схемы skill SHALL предоставлять отдельный store-модуль с полной корневой композицией и типизированным context-доступом. Bootstrap SHALL создавать один store на экземпляр приложения. Потребители MUST сохранять реактивное чтение полного state и общий dispatch через публичный accessor без импорта bootstrap или runtime-циклов. Схема SHALL быть явной адаптацией границ проекта.

#### Scenario: Connect business components
- **WHEN** два бизнес-компонента получают store через context
- **THEN** оба используют один экземпляр с типизированным полным state и dispatch
- **AND** изменение одной из двух синтетических частей состояния наблюдаемо потребителями
- **AND** shared UI получает готовые props/callbacks, не импортируя состояние бизнес-фич

#### Scenario: Provider ownership
- **WHEN** bootstrap создаёт подключение
- **THEN** provider устанавливается при инициализации корневого компонента
- **AND** создание store и сборка reducers/effectors отделены от публичного доступа компонентов
- **AND** корневые контракты не переносятся в shared для обхода направления импортов

#### Scenario: Isolate application instances
- **WHEN** два экземпляра приложения подключены одновременно
- **THEN** каждый имеет свой store
- **AND** dispatch в одном не меняет состояние другого

#### Scenario: Missing provider
- **WHEN** компонент запрашивает store без provider
- **THEN** подключение выдаёт понятную диагностику отсутствующего context
- **AND** не создаёт запасной store автоматически

#### Scenario: Preserve existing access conventions
- **WHEN** проект уже имеет совместимое подключение или другую согласованную архитектуру
- **THEN** skill учитывает её при проверке и повторном применении
- **AND** не вводит второй store/provider и не навязывает модульную схему всем Svelte-проектам
